# Streamlit–FastAPI 통합 프로젝트 개발 계획서

## 1. 문서 목적

이 문서는 현재 분리되어 있는 `frontend`(Streamlit)와 `backend`(FastAPI) 프로젝트를 하나의 서비스로 연동·확장하기 전에 개발 범위, 우선순위, 인터페이스, 검증 기준을 합의하기 위한 계획서다.

현재 코드는 주요 화면과 API의 동작을 확인하는 목업 단계이므로, 실제 개발에서는 하드코딩된 데이터와 인증 로직을 제거하고 백엔드 API 및 영속 데이터 저장소를 기준으로 기능을 완성한다.

## 2. 현재 프로젝트 분석

### 2.1 프런트엔드

- 기술: Python, Streamlit, httpx, pandas
- 구현 화면:
  - 홈 및 요약 지표
  - 로그인
  - 회원가입
  - 외부 Open-Meteo API를 이용한 날씨 조회
  - FastAPI 서버 상태 확인 화면
- 현재 제약:
  - 로그인 계정이 `id01`/`pwd01`로 하드코딩되어 있다.
  - 회원가입 정보가 저장되지 않는다.
  - 상품 및 Gemini 채팅 화면이 없다.
  - 백엔드 주소가 소스에 직접 작성되어 있다.
  - 로그인 상태가 브라우저 저장소의 문자열에만 의존한다.

### 2.2 백엔드

- 기술: Python, FastAPI, Pydantic, Uvicorn, pytest, Google GenAI SDK
- 구현 API:
  - `POST /chat/gemini`
  - `POST /product/create`
  - `GET /product/get/{product_id}`
  - `GET /product/getall`
  - `PUT /product/update/{product_id}`
  - `DELETE /product/delete/{product_id}`
- 현재 제약:
  - 상품 데이터가 서비스 코드의 고정 응답이며 데이터베이스에 저장되지 않는다.
  - 사용자 가입·로그인 API가 없다.
  - 프런트엔드가 호출하는 `GET /health`가 구현되어 있지 않다.
  - Gemini 키 누락, 외부 API 실패 등에 대한 예외 처리가 부족하다.
  - 일부 API 경로와 HTTP 메서드가 일반적인 REST 규칙과 다르다.
  - 상품 테스트는 조회·생성 위주이며 수정·삭제·실패 사례가 부족하다.

## 3. 개발 목표

1. Streamlit 화면과 FastAPI API를 안정적으로 연동한다.
2. 회원가입, 로그인, 로그아웃 및 인증이 필요한 화면 접근 제어를 구현한다.
3. 상품 등록·목록·상세·수정·삭제 기능을 실제 데이터 저장소와 연결한다.
4. 로그인 사용자가 Gemini 채팅을 이용할 수 있도록 한다.
5. 설정과 비밀값을 환경 변수로 분리하고 오류 처리 및 로깅을 표준화한다.
6. 자동화 테스트와 실행 문서를 갖춘 재현 가능한 개발 환경을 만든다.

### 필수 범위(MVP)

- 백엔드 상태 확인 API

- 회원가입·로그인·로그아웃
- 사용자와 상품 데이터 영속 저장
- 상품 CRUD 화면과 API
- Gemini 단일 턴 채팅 화면과 API
- 입력 검증, 공통 오류 응답, 로깅
- 백엔드 단위·통합 테스트
- 프런트엔드 핵심 로직 테스트
- 로컬 실행 및 환경 변수 문서

### 후속 범위

- Gemini 멀티턴 대화 및 대화 기록
- 사용자 역할과 관리자 화면
- 상품 검색, 정렬, 페이지네이션
- 비밀번호 재설정 및 이메일 인증
- 운영 배포, 모니터링, CI/CD

### 제외 범위

- 결제와 주문 처리
- 실시간 채팅
- 소셜 로그인
- 대규모 트래픽 최적화

## 6. 기능 요구사항 및 완료 기준

### 6.1 서버 상태 확인

- `GET /health`는 서버 상태와 애플리케이션 버전을 반환한다.
- 프런트엔드는 성공, 연결 실패, 시간 초과를 구분해 표시한다.
- 완료 기준: 백엔드 실행 여부에 따라 화면에 올바른 메시지가 표시되고 테스트가 통과한다.

### 6.2 회원가입 및 인증

- 회원가입 입력값: 아이디, 비밀번호, 이름
- 아이디 중복을 차단한다.
- 비밀번호는 평문으로 저장하지 않고 안전한 해시로 저장한다.
- 로그인 성공 시 접근 토큰 또는 안전한 세션 정보를 발급한다.
- 인증 실패 사유를 사용자에게 노출하되 내부 보안 정보는 노출하지 않는다.
- 로그아웃 시 프런트엔드 세션과 인증 정보를 제거한다.
- 완료 기준: 가입 → 로그인 → 보호 화면 접근 → 로그아웃 흐름이 정상 동작한다.

### 6.3 상품 관리

- 상품 필드: 식별자, 이름, 가격, 생성일, 수정일
- 이름은 필수이며 가격은 0 이상의 정수로 제한한다.
- 상품 목록, 상세, 등록, 수정, 삭제를 지원한다.
- 존재하지 않는 상품은 `404`, 잘못된 입력은 `422`로 처리한다.
- 권장 API:
  - `POST /products`
  - `GET /products`
  - `GET /products/{product_id}`
  - `PATCH /products/{product_id}`
  - `DELETE /products/{product_id}`
- 완료 기준: 프런트엔드에서 전체 CRUD 흐름이 실제 저장소에 반영된다.

### 6.4 Gemini 채팅

- 로그인 사용자가 질문을 입력하고 응답을 확인할 수 있다.
- 빈 질문, API 키 누락, 요청 시간 초과, 모델 오류를 구분해 처리한다.
- API 키와 내부 오류 상세는 화면 및 응답에 노출하지 않는다.
- 요청 로그에 질문 전문이나 개인정보를 무분별하게 기록하지 않는다.
- 완료 기준: 모의 테스트와 실제 개발 환경 호출이 모두 성공하며 실패 시 복구 가능한 안내가 표시된다.

### 6.5 날씨 조회

- 현재 기능을 유지하되 외부 API 호출 코드를 별도 서비스 또는 클라이언트로 분리한다.
- 조회 중, 성공, 빈 응답, 시간 초과, 연결 실패 상태를 명확히 표시한다.
- 완료 기준: 1~7일 조회와 표·차트 표시가 정상 동작한다.

## 7. 데이터 모델 초안

### User

| 필드 | 형식 | 규칙 |
|---|---|---|
| id | UUID 또는 정수 | 기본 키 |
| username | 문자열 | 필수, 고유값 |
| password_hash | 문자열 | 필수, 평문 저장 금지 |
| name | 문자열 | 필수 |
| created_at | 날짜/시간 | 서버 생성 |

### Product

| 필드 | 형식 | 규칙 |
|---|---|---|
| id | UUID 또는 정수 | 기본 키 |
| name | 문자열 | 필수 |
| price | 정수 | 0 이상 |
| created_at | 날짜/시간 | 서버 생성 |
| updated_at | 날짜/시간 | 서버 갱신 |

데이터베이스는 현재 의존성에 포함된 Supabase를 우선 후보로 검토하되, 교육·로컬 실행 편의가 더 중요하면 저장소 인터페이스를 유지한 채 SQLite로 시작할 수 있다. 구현 전 한 가지 방식을 확정한다.

## 8. 비기능 요구사항

- 설정: `API_BASE_URL`, `GEMINI_API_KEY`, `GEMINI_MODEL`, 데이터베이스 연결 정보는 환경 변수로 관리한다.
- 보안: 비밀값 커밋 금지, 비밀번호 해시, 인증 만료, 입력값 검증을 적용한다.
- 안정성: 외부 호출에 타임아웃을 지정하고 예외를 사용자용 메시지로 변환한다.
- 로깅: 요청 ID, 상태 코드, 처리 시간을 기록하며 비밀번호·토큰·API 키는 제외한다.
- 품질: 공개 함수에 타입 힌트를 적용하고 라우터·서비스·저장소 책임을 분리한다.
- 호환성: 프런트엔드와 백엔드의 `httpx` 버전 등 공통 의존성 충돌을 사전에 확인한다.
- 문서화: 실행 방법, 환경 변수, API 사용법을 README 및 OpenAPI 문서에 반영한다.

## 9. 단계별 개발 계획

### 1단계 — 기반 정비

- 현재 소스 인코딩과 문법 상태 점검
- 공통 환경 변수 및 `.env.example` 작성
- 백엔드 CORS, 공통 예외 처리, 로깅 설정
- `GET /health` 구현
- 프런트엔드 공통 API 클라이언트 작성

완료 조건: 두 서버를 로컬에서 실행하고 프런트엔드의 서버 체크가 성공한다.

### 2단계 — 데이터 저장 및 인증

- 데이터베이스 방식 확정 및 스키마 생성
- 사용자 저장소·서비스·API 구현
- 비밀번호 해시 및 인증 토큰/세션 처리
- 회원가입·로그인 화면을 API에 연결
- 인증이 필요한 페이지의 접근 제어 적용

완료 조건: 재시작 후에도 사용자가 유지되며 정상·실패 인증 시나리오 테스트가 통과한다.

### 3단계 — 상품 CRUD 통합

- 하드코딩된 상품 서비스를 저장소 기반으로 교체
